# Run in the browser with Pyodide, self-hosted, with Numba optional only there

The website's playground lets people try MarketForge before installing it. We considered porting the simulator to JavaScript and rejected it: it would be a second implementation of the model to keep in step with the first, validated by nothing. The playground instead runs the released wheel itself in [Pyodide](https://pyodide.org/) (CPython compiled to WebAssembly), which ships numpy, pandas, pyarrow and the other dependencies, but not Numba: LLVM cannot target WebAssembly from inside the browser. So Numba is a dependency everywhere except `sys_platform == "emscripten"`, and only there do the kernels run as plain Python. That gives the same bits as the compiled kernels (ADR 0007 forbids anything Python could not reproduce exactly), at 10 to 100 times the time. On every other platform a missing Numba still fails at import instead of falling back, since a silent fallback would make a broken install 30 times slower without saying why. The site serves Pyodide and its wheels itself, downloaded at build time and checked against Pyodide's lock-file hashes, so visitors contact no third party (the privacy policy promises it) and the version cannot drift under the page. WebAssembly is a separate platform in the sense of ADR 0011: numpy's `exp` and `log` there differ from the SIMD versions in the last bit, so the playground's candles are not bit-identical to an installed MarketForge's for the same seed and version, and the page says so before anyone generates anything. Its requests are capped to what a browser tab can simulate in about half a minute; datasets that matter are generated with the installed package.
